A. 通用开发提示词（可直接复用）

A1. 【改内嵌 HTML 的一次性补丁脚本】—— 本项目铁律
--------------------------------------------------------------------------------
提示词：
  修改内嵌在某容器（APK / 单文件程序 / 固件）里的 HTML 时，按下面做：
  1. 基线永远从「上一版已发布的成品」里读（如 zip 读 APK 里的 assets/dashboard.html），
     不要读上次脚本的输出，否则脚本无法重复执行。
  2. 读进来先做行尾归一：replace("\r\n","\n").replace("\r","\n")。
     容器里的文件常是 CRLF，按 "\n" 切出来的每行尾部带 "\r"，
     多行字符串匹配会永远对不上（本项目为此卡了两轮）。
  3. 所有改动写成 (old, new, 标签, 是否必须命中) 的列表，
     每条替换后打印命中次数；必须命中的项没命中就立刻 sys.exit(1)，
     绝不允许「静默跳过」继续往下跑 —— 静默跳过必然产出半成品。
  4. 不要用多个 Edit 并行改同一个大文件，容易丢改。
  5. 改完必须自检：
     - 剥掉 <script>…</script> 后统计 <div> 与 </div> 数量，必须相等；
     - 列负面清单，断言已删除的东西确实为 0；
     - 列正面清单，断言新增标记确实存在；
     - 抽出行首的 <script> 块跑 node --check（注意：注释里常出现字面量
       "<script>"，必须只匹配「行首的 <script」标签，否则误报）。
  6. 最后再走一次「打包 → 校验」闭环，版本号在打包脚本和校验脚本里同步升。

A2. 【CSS 特异性压不住 = 设置项失效】
--------------------------------------------------------------------------------
提示词：
  写「用户可调字号/颜色」类功能时，先算清楚选择器特异性，再决定注入规则怎么写。
  特异性：ID(1,0,0) > class/属性/伪类(0,1,0) > 元素(0,0,1)；同分时后写的胜。
  本项目的两个真实故障，都是「注入规则的特异性低于页面原有规则」：
    · 底部三键字号失效（v15）：
        页面原有：#btnBar .btn-ai, #btnBar .btn-radio = (1,1,0)，36px
                  #btnBar .gear-btn                = (1,1,0)，30px
        引擎注入：#btnBar button                    = (1,0,1)
        (1,1,0) > (1,0,1) → 注入的永远压不住，拖动设置没反应。
        修法：把注入选择器提升为 #btnBar button.btn-ai / .btn-radio / .gear-btn
              = (1,1,1)，压过原有的 (1,1,0)。
    · 新闻字号「中文能调、英文调不了」（v16）：
        页面原有：.news-title.t-long = (0,2,0)，24px（标题 >40 字时命中）
        引擎注入：.news-title        = (0,1,0)
        (0,2,0) > (0,1,0) → 英文标题（普遍 >40 字）被锁死在 24px。
        修法：补一条同级的 .news-title.t-long 规则，并让它复用同一个倍率键。
  教训：**给同一元素补规则时，先把页面上所有会命中它的选择器列出来比大小**，
  不要凭直觉以为「后注入的就生效」；同分时才是后写的胜。

A3. 【界面字号要「统一 + 可单独调」时的正确结构】
--------------------------------------------------------------------------------
提示词：
  需求若是「A/B/C 三个界面字号默认一致、且能统一调或单独调」，按下面设计：
  1. 单一基准值 + 系统倍率 + 每界面倍率：
     最终字号 = 基准px × sysFactor × uiFont[界面]/100
     三者默认都是 100%，开箱即「三界面一致且随系统字号缩放」。
  2. 规则在运行时由 JS 注入（不要写死在 CSS 里），否则倍率改不了。
  3. 注入时用 !important 通配（#xxx, #xxx * { font-size: Npx !important }）。
  4. **凡是被 !important 通配覆盖的界面，里面所有「自己设 inline 字号」的代码
     都会失效**（作者样式里的 !important 胜过非 important 的内联样式）。
     必须把那些 inline 设置改成走同一套引擎，否则出现「设置了没反应」。
  5. 一个设置项只能有一个数据源。不要让两处 UI 各自写同一个字段，
     否则一侧读 16/20/26（px）、另一侧读 85/100/130（%），互相打架。

A4. 【「默认值」和「一次性迁移」要分清】
--------------------------------------------------------------------------------
提示词：
  改某个用户可改配置的默认值时，必须同时考虑「老用户机器上已经存了旧值」：
  1. 只改代码里的默认值，对老用户无效（他们 localStorage 里已有旧值）。
  2. 必须配一个一次性迁移标记（storeGet/storeSet 一个只跑一次的 key），
     在迁移里把旧值升到新值；之后完全尊重用户的改动。
  3. 迁移要幂等（用标记位保证只跑一次），且要能区分
     「从来没设过」和「用户主动清空」—— 后者不要硬塞回默认值。
  4. 反面案例：本项目 alertCfg() 里有个「首次读取锁汕头」的逻辑，
     它会在每次新装时把地区写死成汕头，把新默认值覆盖掉；
     改默认值为广东后，还必须额外加一条迁移把已装设备的 shantou 升成 guangdong，
     否则老设备永远看不到预警。

A5. 【功能「常年不出现」时，先怀疑过滤条件而不是接口】
--------------------------------------------------------------------------------
提示词：
  排查「某个提醒/列表常年空白」时，按这个顺序：
  1. 先用真实数据打一遍：把接口的真实返回喂给过滤+渲染函数，看命中几条。
     （本项目实测：中央气象台按省返回 16 条广东预警，
      但过滤条件要求标题里出现「汕头」二字 → 命中 0 条。）
  2. 把过滤条件的「粒度」和接口的「粒度」对齐：接口按省返回，就别按市去过滤。
  3. 独立性检查：不要把两个不同的功能绑在同一个开关上。
     （本项目「极端天气提醒」被挂在「只看官方机构」下面，
      而后者默认开 → 极端天气永远被排除。）
  4. 写可执行的回归测试：把纯函数抽出来在 node 里跑，
     用真实数据断言「命中数 > 0」「渲染文案非空」「关掉开关后为空」。

A6. 【「列表显示不全」先查有没有硬编码截断】
--------------------------------------------------------------------------------
提示词：
  需求是「清单要完整呈现、新增项也要能显示」时，全局搜这几类硬编码：
    · .slice(0, N) / .splice(0, N) / .substring(0, N)
    · for 循环里的 `if (list.length >= N) { break; }`
    · LIMIT / TOP / pageSize 常量
  本项目有两处：预设电台库 934 条但只渲染前 80 条、搜索结果到 60 条就 break。
  改成全量后要评估老设备性能；如果确实太大，改成「默认全量 + 搜索过滤」，
  不要偷偷截断。

A7. 【「选了但保存不了」= 缺保存入口】
--------------------------------------------------------------------------------
提示词：
  表单类需求要检查完整链路：控件 → 读取 → 写配置 → 落盘 → 回执。
  最常见的断点是「有控件、没有保存按钮」，值只在下一次别的操作里被顺带读走，
  用户就会认为「选了没用」。
  修法：给控件旁边加【确定】按钮，点了立刻 saveConfig() + 可见回执（Toast/文案）。
  另外老安卓/墨水屏上 <input type="number"> 体验很差，
  改成 <select> 给固定档位更可靠，回填时对老值做档位兜底。

A8. 【打包时最容易漏的：HTML 引用了但包里没有的资源】
--------------------------------------------------------------------------------
提示词：
  重新打包前，把 HTML 里所有 <script src="..."> / <link href> / url(...) 的
  引用项列出来，逐条确认成品包里存在。
  本项目真实事故：底包里没有 assets/hls.min.js 与 assets/radio_presets.js，
  而页面引用了它们 → RADIO_PRESETS 恒为 undefined →
  「电台清单一直是空的」，用户反馈了很久才发现。
  修法：打包脚本里做「补齐缺失 assets」的步骤，并在校验脚本里断言这些条目存在。
  **这类问题不会报错，只会静默失效，必须显式断言。**

A9. 【老设备（Android 4.0 / 墨水屏）兼容红线】
--------------------------------------------------------------------------------
提示词：
  目标含 Android 4.0~4.3 时，逐条对照：
  · JS 只写 ES3/ES5：禁用 let/const/箭头函数/class/模板字符串/反引号。
    扫描时注意误报：诗歌文本和注释里常出现 "let " 和反引号。
  · CSS 不用 var()/calc 的复杂组合做关键布局（老 WebKit 支持不全）；
    本项目全站用 calc(Npx * var(--sys,1))，若 var 不支持整条声明会被丢弃，
    因此关键尺寸必须有兜底。
  · 不用 inset 简写（老 WebKit 会塌成 0×0）→ 用 top/left/right/bottom。
  · APK 必须 v1(JAR) 签名，摘要属性名写 SHA1-Digest（无连字符）。
    同时**必须**带 v2 签名块：targetSdk ≥ 30 时 Android 11+ 强制校验 v2，
    只签 v1 会「安装包解析失败 / 无法安装」。老机器按 EOCD 找 CD，
    会把夹在「最后条目」与 CD 之间的 v2 块当空隙跳过，对 4.x 完全无害。
  · resources.arsc / classes.dex / launcher png 必须 STORED 且数据起始 4 字节对齐。
    **对齐要写进 local header 的 extra field，不能在数据前裸填 0x00**
    （裸填充的 extraLen=0，数据相对 header 的偏移对不上，11+ 直接拒装）。
  · Android 12+ 要求所有带 intent-filter 的组件显式写 android:exported。
  · 无 native .so 时不受 16KB 页对齐影响。
  · minSdk 决定下限，targetSdk 决定上限行为；本项目 minSdk14 / targetSdk34，
    实测可覆盖 Android 4.0 ~ Android 16。

A10. 【改二进制 AndroidManifest.xml 的正确姿势】
--------------------------------------------------------------------------------
提示词：
  没有 apktool/aapt 时改 AXML：
  1. 字符串以 UTF-16LE 存于字符串池，每条前面有 2 字节长度前缀，后面有 2 字节 0 终止。
  2. 修改必须**保持总字节数不变**：改长度前缀、短出来的用 0 填充补在终止符后。
     因为后面所有字符串用的是绝对偏移，一旦总长变了全部作废。
  3. 改完立刻用自己的解码器重新解析一遍，断言「只有目标字符串变了，
     其余 N 条完全一致」，再用 androguard 之类的第三方解析复核。
  4. 改不动的（如 versionCode 这类整型属性）就不要改，收益低于风险。

================================================================================
B. 本项目逐条踩坑实录
================================================================================

B1. 行尾 CRLF 导致多行替换永远匹配不上
  现象：apply_v14b.py 报 AssertionError: jumpSec head not found。
  根因：APK 里的 assets/dashboard.html 是 CRLF，按 "\n" split 后每行带 "\r"。
  修法：读进来先 replace("\r\n","\n").replace("\r","\n")；
        并且把多行匹配改成「单行定位 + 按行插入」，比整块字符串替换稳。

B2. 老 WebKit 的 div 数量必须严格配平
  现象：设置页少一个 </div>，整页错版。
  修法：用「深度配对」找 div 的闭合位置，不要用 -3 之类的估算。
        脚本跑完必须统计非 script 区域的 <div> 与 </div> 数量并断言相等。

B3. 脚本不可重复执行
  现象：apply_v16.py 第一版直接读自己上一次的输出当基线，第二次跑就全乱。
  修法：基线固定从上一版成品包（zip）里读，输出单独写。

B4. 底部三键字号失效（v15）
  根因：注入的选择器特异性不够，被页面上更具体的规则压住。
  修法：提升到 #btnBar button.btn-ai / .btn-radio / .gear-btn。

B5. 新闻字号「中文能调、英文调不了」（v16）
  根因：英文标题 >40 字 → .news-title.t-long(0,2,0) 压过注入的 .news-title(0,1,0)。
  修法：FONT_RULES 增加 ["newsTitleLong", [".news-title.t-long"], 24]，
        并在 applyFontSizes 里把 newsTitle* 前缀映射到同一个倍率键。
  实测：130% 时 27.6→35.88、24→31.2；70% 时 →19.32 / 16.8，中英同步。

B6. 后台三界面字号（v16）
  需求：Radio / AI / 设置页三界面字号一致且跟系统字号一致，且可统一或单独调。
  做法：基准 22px × sysFactor × uiFont{radio,ai,set}，JS 运行时注入 4 条 !important 规则。
  连带修复：AI 界面原本用 inline 设字号，被 !important 盖掉后失效 →
            改为 aiApplyFont() 只调 applyUIFontSizes()；
            旧的「AI 字号 小/中/大(16/20/26)」下拉改成百分比，与界面字号同源。
  实测：默认三者 22；系统 1.5 倍 → 33；只调电台 130% → 电台 42.9 其余 33；
        统一 85% → 三者 28.05。

B7. 极端天气 / 灾害提醒不上主页（v16）
  根因一：alertCfg() 默认 region="shantou"，而接口按广东省返回 → 命中 0 条。
  根因二：地区被「首次读取锁汕头」的逻辑写死，改默认值对老设备无效。
  根因三：「极端天气」被绑在「只看中国权威机构(默认开)」下面 → 永远排除。
  修法：① 默认值改 guangdong（汕头条目 rank=2 仍排最前）；
        ② 锁汕头的逻辑改成锁广东；
        ③ 加一次性迁移 kd_alert_gd_20260919a 把老设备的 shantou 升成 guangdong；
        ④ 极端天气独立开关 stAlertExtreme，默认开。
  实测（真实 nmc.cn 数据）：广东档命中 8 条，渲染「广东预警：…」；
        极端天气命中「暴雨 大暴雨」；关掉开关后为空；再打开又出现。

B8. 电台清单为空（v16）
  根因：APK 里根本没有 assets/radio_presets.js（底包没有，打包脚本也没补），
        页面却 <script src="radio_presets.js"> → RADIO_PRESETS 恒为 undefined。
        同时 assets/hls.min.js 也缺失。
  修法：打包脚本增加「补齐 HTML 引用但底包缺失的 assets」步骤；
        校验脚本断言这两个条目存在且含 WLTW/NPR。
  其它：预设库 934 条原本只渲染前 80 条、搜索到 60 条 break → 改全量；
        设置页补上「我的电台清单」容器（与 Radio 界面共用渲染函数）。

B9. 播放时长选了保存不了（v16）
  根因：只有 <input type="number">，没有保存按钮；值要等到下次播放才被读走。
  修法：改成 <select> 固定档位（不限时/10/15/30/45/60/90/120）+【确定】按钮
        radioDurSave()：立刻写 CFG.radio.duration + saveConfig + Toast 回执；
        设置页同样改下拉，并提供 radioDurSaveSettings() 即时保存。

B10. RSS 预设与备链（v15/v16）
  v15：停掉启动/保存时的自动补备链、删掉「补齐到 N 条」按钮、
       删死代码 backupFillers/ensureBackupMin/ensureAllBackups 与 BACKUP_MIN，
       加一次性迁移清空已存备链。
  v16：预设源由 9 个增到 10 个（谷歌全球新闻 googlenews.buzzing.cc/feed.xml），
       同步改 DEF_RSS_SOURCES 与 PRESET_RSS，并加一次性迁移
       kd_rss10_20260919a 只补这一条（不重置用户已有的增删改，按 URL 去重）。

B11. 设置页整合（v16）
  · 去掉顶部五个大类跳转按钮（与下面可点开的分区标题重复）。
  · 「网络诊断」从「新闻资讯」归入「本机常驻」。
  · 新增「界面字号」分区（三界面统一 + 各自微调）。
  · 新增「关于与版权」分区（程序名 / 作者 / 版本号 / 版权声明 / 免责声明）。
  · 电台区补上「我的电台清单」。
  · 分区增删后必须同步 resetCats() 里的默认展开表，否则新分区状态不对。

B12. 版本号与版权（v16）
  · HTML 内新增 KD_APP_NAME / KD_APP_AUTHOR / KD_APP_VERSION 三个常量，
    「关于」页直接读它们显示，避免与 APK 文件名不一致。
  · 二进制 AndroidManifest.xml 里的 versionName 由 V6.8 就地改成 V16
    （UTF-16 字符串池定长替换，改完用解码器 + androguard 双重复核）。

B13. 部分机器「签名 / 安装包有问题」装不上（v17）
--------------------------------------------------------------------------------
现象：同一版 APK，新一点的安卓机器报签名或安装包错误，老机器反而能装。
根因（两个，缺一不可）：
  1. 只做了 v1(JAR) 签名。targetSdk=34 时 Android 11+ 强制要求 v2 签名方案，
     没有 v2 块 → 直接拒绝安装。
  2. 手写 ZIP 时为了 4 字节对齐，在 STORED 条目数据前裸填 0x00。
     zipalign 要求把填充写进 local header 的 extra field（extraLen 同步加），
     裸填充会让「数据相对 header 的偏移」对不上，校验不过。
修法：
  · 纯 Python 实现 APK Signature Scheme v2（RSASSA-PKCS1v15 + SHA-256，
    内容摘要用 CHUNKED_SHA256），块夹在最后条目与 CD 之间。
  · 对齐改写 extra field。
  关键坑（写实现时全踩过）：
  · 块的 size 字段语义是「块总长 − 8」，不是块总长，写错就整体偏 8 字节。
  · signers 是**两层** length-prefix：signer = lp(signedData) + lp(signatures) + lp(pubkey)。
  · 校验时 magic 在 EOCD 前 16 字节处、block size 在 EOCD 前 24 字节处。
  · 必须有独立的校验脚本，重算内容摘要 + 用证书公钥真验签，
    而不是只看「有没有 magic」。
验收：v1 + v2 都过，且 minSdk 14 / targetSdk 34 可覆盖 Android 4.0~16。

B14. 日历改造：删标题、删本月一览、节日直接进格子（v18）
--------------------------------------------------------------------------------
需求：去掉日历上方「日历」两字、去掉下方「本月节日」，节日写进具体日期格子里
      （中外主要节日都要），日期之间更疏朗，节日字再小一点。
做法：
  1. 节日数据分两类，一眼就能看出该改哪儿：
     · 公历固定节日 SOLAR_FEST：键 "月-日"，值为 [格子短名, 完整名]。
       中外都要有：元旦/妇女/植树/愚人/地球/读书/青年/护士/儿童/环境/
       建党/建军/教师/国庆/万圣/平安/圣诞/情人/劳动/消权。
     · 浮动节日（按「第 n 个星期 w」推算）：母亲节=5 月第 2 个周日、
       父亲节=6 月第 3 个周日、感恩节=11 月第 4 个周四。
       算法：day = 1 + ((w - 当月1日星期) + 7) % 7 + (n-1)*7。
  2. 优先级：法定放假 > 法定调休「班」 > 农历传统节日 > 公历节日 > 农历日。
     公历节日排最后一道，才不会把春节、中秋顶掉。
  3. **格子窄是硬约束**：左栏 40%、7 列、table-layout:fixed，
     每格可写区只有约 28 设计单位。所以节日名一律压到 2 字
     （统一走 festShort() 截断，完整名留在 name 里），
     3 字以上会被 overflow:hidden 悄悄裁掉半截 —— 这种失败不报错，只能靠看。
  4. 删掉的东西要连带清干净：标题 div、monthFestSummary()、.cal-fest 的 CSS、
     暗色模式选择器里的 .cal-fest、FONT_RULES 里的 calendar4，
     以及代码注释里「calendar2/3/4 跟随」这类描述。
  5. 疏朗靠 padding：td 内边距 1.2px → 5px（纵向）、2.4px → 3px（横向），
     th 高度 30.7 → 34；删掉的内容腾出的高度正好抵掉，总高度基本不变。
  6. 节日字号 12.8 → 11.2：**CSS 里的 calc() 和 FONT_RULES 里的基准值要同步改**，
     否则引擎写进内联样式的字号会盖掉 CSS。
提示词：
  「日历格子太窄，任何写进格子的文字都按 2 个汉字预算，超了先截断再想措辞；
    字号分档只改一处会失效 —— CSS 与 FONT_RULES 必须成对改。」

B15. 「所有设备都装不上」——自写校验会自欺（v19，本系列最贵的一个坑）
--------------------------------------------------------------------------------
现象：v17 补齐 v2 签名后，本地 26 项校验全绿，用户拿去真机一试，
      几台安卓墨水屏设备**全部**无法安装。
根因：自己写的 v2 签名块结构不合规范 ——
      signed data 里 digests / signatures 的正确结构是
          lp( 序列( lp( u32 算法ID + lp(数据) ) ) )
      即「外层一个 lp 包住整个序列，**每一项自己还要再套一层 lp**」。
      我们只套了外层。Android 解析时会把「算法 ID 0x0101」当成条目长度(257)，
      立刻越界 -> 整个签名块非法 -> 拒装。
最要命的不是写错，而是**验不出来**：
      校验脚本 check_v2 是我们自己写的，用同样错误的结构去解，
      于是「内容摘要一致」「RSA 签名验过」全部 OK，一路绿灯。
      自写校验只能证明「自己跟自己对得上」，证明不了「跟规范对得上」。
      （v17 的校验当时就是这样"通过"的，v18 又照抄了一遍。）
修法：
  1. 修实现：digests / signatures 每项补内层 lp。
  2. 修校验：解析同步改对 —— 否则修完实现，校验反而会报错（好事，说明它开始较真了）。
  3. **接入第三方独立解析器做交叉验证**（本项目用 apksigtool，pip 即可装）：
        pip install apksigtool
        取**整个签名块**（含首尾 uint64 size + 16 字节 magic）传进去，
        apksigtool.parse_apk_signing_block(blk)
      只传 pairs 区会在第一条 assert 就炸，别搞错入参。
      Pair 是 namedtuple (length, id, value)；signer 上是 .signatures，
      signed_data 上是 .digests / .certificates。
  4. 把交叉验证**写进 verify_a5.py 的常规流程**（[6] 段），不是想起来才跑一次。
教训（提示词）：
  「凡是自己实现二进制格式，就必须找一个别人写的解析器来交叉验证。
    只用自己的解析校验，等于没校验 —— 实现者和校验者犯同一个错，
    两边会一起错，而且错得整整齐齐、全绿通过。」
  「校验脚本报绿只能说明'自洽'。问自己一句：
    这个'通过'有没有可能只是我和我自己在互相点头？」

B16. v2 内容摘要算法写错 = 比结构更隐蔽的第二层自欺（v20）
--------------------------------------------------------------------------------
现象：v19 把「结构」修对（补了内层 lp），本地 28 项校验又全绿，
      用户拿去真机 —— 海信 A5 报「103」、Android 13 报「安装包有问题」，**还是全拒装**。
根因：这次不是结构，而是 **APK Signature Scheme v2 的内容摘要算法**写错。
      规范：每个 1MB 分块 chunk = H(0xa5 + u32(len) + chunk)，
            顶层摘要 = H(0x5a + u32(总块数) + 各块摘要依次拼接)。
            **三个区段（条目区 / Central Directory / EOCD）在「分块」层面拼接。**
      旧 _digests_of 写成：先对每个区段各自做一次顶层哈希，再把三段哈希拼起来二次哈希
            —— 与 Android 算出的完全不同。Android 算出正确摘要、与签名块内比对不符 -> 拒装。
      同样是自欺：check_v2 用**同一套错误算法**重算，于是「摘要一致」「验签通过」继续全绿。
修法（apk_sign_v2._digests_of）：
      三个 region 各自按 1MB 切块收集 chunk_digest，再
      top = H(0x5a + u32(len(chunk_digests)) + b"".join(chunk_digests))。
独立核对（关键，防自欺）：
      用第三方 apksigtool 自己的 apk_digest_chunked(apk, sb_offset, hashlib.sha256)
      重算摘要，与签名块内 digests 里对应算法 ID（v20 误标 0x0101，v21 修正为 0x0103）的摘要**逐字节**比对，一致才放行。
      ⚠️ apksigtool 的 HASHERS 表**正确**注册了 0x0103/0x0104 = PKCS1v15（本工程实际用的就是它），能正常处理；
      早期我们给它 monkeypatch 0x0101→PKCS1v15 反而制造假绿（详见 B17）。
      它的 apk_digest_chunked 与 HASHERS 无关、是按规范实现的，可放心借来比摘要。
      现成脚本 verify_apksigtool.py 已正确抽取签名块 + 比摘要 + 用 cryptography 独立验 RSA 签名。
教训：
  「交叉验证不能只 parse，必须比『值』。光结构能解、摘要写错，parse 一样绿、设备照样拒。」
  「自写二进制格式 + 自写校验，永远要找一个**按规范独立实现**的第三方去比最终数值
    （摘要 / 解析结果 / 字节），而不是只比『能不能解开』。」

B17. v2 签名算法 ID 错配 = v17→v20 全拒装的唯一真根因（v21，本系列最贵）
--------------------------------------------------------------------------------
现象：v19 修结构、v20 修内容摘要算法后，本地几十项校验全绿（自写 + apksigtool），
      真机仍全拒装（海信 A5 错误 103 / Android 13「安装包有问题」）—— 与 v17~v19 现象完全一致。
根因：v2 签名块里的「算法 ID」与实际签名算法不一致，且这是 v17→v20 **唯一跨版本恒定的真因**：
      Android 官方 apksig 算法 ID 规范（已被官方 apksigner 实测确认）：
        0x0101 / 0x0102 = RSASSA-**PSS**        (+SHA256 / +SHA512)
        0x0103 / 0x0104 = RSASSA-**PKCS1-v1_5** (+SHA256 / +SHA512)
      旧 apk_sign_v2.py 把 ID 标成 0x0101（误以为 PKCS1v15），但签名用 cryptography 的 PKCS1v15 算的。
      Android 按 ID=0x0101 当 PSS 验 -> NoSuchAlgorithmException / 签名不匹配 -> 拒装。
      之前 v19 把「结构」、v20 把「摘要算法」当根因去修，都打了偏靶——根因在算法 ID，修别处永远无效。
      （注：v20 修的「内容摘要算法」其实是对的，apksigtool.apk_digest_chunked 重算与块内一致，无需回退。）
修法（apk_sign_v2.py）：
      SIG_RSA_PKCS1V15_SHA256 = 0x0103、SIG_RSA_PKCS1V15_SHA512 = 0x0104；
      内容摘要继续用 CHUNKED_SHA256。改后官方 apksigner 输出 Verifies（v1/v2 均 true）。
权威裁判（避免再自欺）：
      在 .workbuddy/binaries/android 部署 JRE17 + build-tools 33.0.2（含 android-13/lib/apksigner.jar），
      封装为 verify_apksigner.py，并接入 verify_signing.py 的 check_apksigner()（[6b] 段）。
      判定标准：apksigner 返回 0 且 stdout 含 "Verifies"。自写校验 / apksigtool 绿了都不算数，
      只有官方 apksigner Verifies 才算真机可装。
      ⚠️ 切勿给 apksigtool 打错 monkeypatch（曾把 0x0101 强行映射成 PKCS1v15 制造假绿，被官方一票否决）。
教训：
  「v2 算法 ID 必须与实际签名算法一致：0x0101 是 PSS，不是 PKCS1v15；PKCS1v15 用 0x0103。」
  「自写校验全绿 = 自洽，不等于合规。二进制格式必须有第三方 + 官方工具双重交叉验证才算数。」
  「同一现象反复出现，先找『跨版本恒定』的那一个错，别在每次表象上打补丁。」
